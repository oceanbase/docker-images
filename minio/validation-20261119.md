## 修复内容

- MinIO 增加 ob-operator 分布式 Helm 所用的 `/minio/health/lakehouse-ready`
  GET/HEAD 端点。新进程须确认三个存储端点可用后才接收流量；已接收流量的存活
  节点仍按写仲裁判断可用性。测试使用原始 Chart 探针，无须改成 `/cluster`。
- 对象最新版本合并时，若仍有成功读取的元数据、存在不可用副本且不足以确认对象
  不存在，返回可重试的 503，避免错误返回 404。真正不存在的对象仍返回 404。

补丁和范围见 [patches/README.md](patches/README.md)。该自定义探针面向单 pool、
单 erasure set、三个 drive 的 Chart 布局；其他布局使用标准 MinIO 探针。
MinIO 上游版本仍为 `RELEASE.2025-10-15T17-29-55Z`，mc 为
`RELEASE.2025-08-13T08-35-41Z`；mc 源码和二进制未修改。
两个组件的完整中英文声明保持不变，原始源码、补丁、修改后源码和构建材料均归档。

Kubernetes 节点容器。两套均使用 K3s、Helm 分布式模式、三个 MinIO Pod、每 Pod
一个持久卷，Pod 分别分配到三个 Kubernetes 节点。ARM 结果不代表物理主机级容灾。

## 持续读取结果与边界

使用带 S3 签名的直接 GET，持续读取已有小对象和故障期间上传成功的小对象，并
逐次比较响应内容；覆盖节点离线、重加入及九次 Pod 重建。每次完整对象回读还会
清空客户端回读目录，避免旧副本掩盖问题。

| 架构 | HTTP 200 | HTTP 503 | 连接失败/超时 | 错误 404 | 内容错误 |
| --- | ---: | ---: | ---: | ---: | ---: |
| amd64 | 3815 | 62 | 140 | 0 | 0 |
| arm64 | 4462 | 251 | 32 | 0 | 0 |

没有再出现“对象存在却返回不存在”或数据内容错误。切换窗口仍有可重试的 503
和连接失败，不能据此声称零中断；每次恢复后的完整对象读取与最终 SHA256 校验均通过。
针对真正不存在的对象，单节点离线时两套环境仍正确返回 404。

首轮监测脚本在新对象上传完成前就将其加入读取集合，ARM 记录到一次创建前 404。
保留该轮日志后，调整为上传成功才开始监测新对象，并重新执行完整节点故障段及
后续重建测试。上表为修正脚本后的正式窗口；未将首轮记录静默删除。

## 测试包与复测

镜像名分别为 `minio:test-44486091060-<arch>` 和
`minio-mc:test-44486091060-<arch>`，`<arch>` 为 `amd64` 或 `arm64`。
它们是 Docker 离线归档中的本地测试标签，未发布 registry 多架构 manifest。

```bash
gh run download 44486091060 --repo gys-git/docker-images   --pattern 'minio-test-packages-*' --dir packages
```

Actions artifacts 保留七天。下载后在获准的对应架构测试机上核对 `SHA256SUMS`，
将 Docker 归档导入每个 Kubernetes 节点的容器运行时；只在外层 Docker 加载镜像
不会自动导入节点内部的 containerd。

复测顺序：备份客户端对象清单并校验旧数据 → 导入所有节点 → Helm 更新镜像 →
按 Chart 的 OnDelete 策略重建 Pod → 核对实际运行的二进制、声明与探针 →
节点离线读写及恢复 → 连续读取中逐 Pod 重建 → 全体停止再启动 → 比较对象 SHA256、
PVC UID/PV 绑定与存储元数据。保留原 Secret、PVC 和升级前的对象校验清单。
源码回归由 CI 的 `test-source.sh` 完成，原始代码失败是预期的回归证明。
