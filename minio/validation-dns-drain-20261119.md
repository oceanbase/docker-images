# 无上游补丁：DNS 刷新与停机排流复测（2026-11-19）

本轮继续使用 [44492216536 原生双架构测试构建](https://github.com/gys-git/docker-images/actions/runs/44492216536)
的 MinIO、mc 镜像。没有修改上游源码、二进制或独立检查组件，没有推镜像仓库、发布 tag、Release 或 latest。
改动均在 Helm 配置，镜像不需要重新构建；测试再次核验实际 Pod 中的二进制和声明文件。

## 定位证据

前一轮 ARM 的九次错误 404 并非数据丢失。本轮沿用原环境和 105 个对象继续对照：

- 原配置第一组六次 Pod 重建，原始 GET 再次出现 61 次错误 404，集中在 09:46:40–48 UTC；
  前一个 Pod 于 09:46:39 Ready，下一个于 09:46:40 开始删除。
- 原配置第二组三次 Pod 重建，原始 GET 出现 98 次错误 404。服务端跟踪记录到 110 次
  `s3.GetObject` 404（包含原始读与适配器读），全部来自仍运行的 `qa-minio-0`，
  时间为 09:52:42.978–09:52:54.834 UTC；当时删除的是 `qa-minio-2`。
- 因此问题不只是请求打到退出中的 Pod。每次恢复后对象完整，说明返回的“对象不存在”是错误判断。
  第一个跟踪连接因节点退出断开而漏掉第一组失败；随后改成每节点独立连接并自动重连，
  第二组获得了上述服务端证据。跟踪不是故障期间无损采集，原始 GET 是验收依据。
- 仅增加 `preStop sleep 10` 后，x86 全套流程中原始 GET 为 10990 次 200、239 次传输失败、0 次错误 404；
  ARM 仍有 11 次错误 404（6428 次 200、21 次传输失败），故中止剩余重复轮次并保留失败证据，继续改配置。

固定版本源码的相关机制（只读分析，没有修改）：`storageRESTClient.IsOnline()` 接受 REST 或 WebSocket
任一通道在线，而带数据的 `ReadXL` 使用 REST。REST 健康重连有最长 30 秒退避；Kubernetes 环境的
DNS 缓存刷新默认也是 30 秒。由此推断，Pod IP 改变后，管理状态/就绪信息恢复可能早于所有读取通路恢复。
服务端跟踪确认了返回错误的存活节点，但本轮没有逐条录制全部内部 RPC，不能把所有内部故障细节当作已证实。

## 最终配置

- `MINIO_DNS_CACHE_TTL=1s`：使用固定上游版本已有的参数，加快变化后的 Pod IP 刷新。
- `preStop: sleep 10`：允许业务 Service 摘除终止中的地址，同时暂时保持 MinIO/S3/节点 RPC 运行。
- `terminationGracePeriodSeconds=40`：等待 10 秒后，仍给原来的终止过程留下 30 秒。
- 保留上轮标准集群探针和独立准入检查。没有改写 404，也没有给原始 GET 加重试。

Pod/EndpointSlice 采样确认：Service 已显示 `ready=false, terminating=true` 时，MinIO 仍保持运行，
实际执行了退出等待。这只能给地址传播和节点恢复提供时间，不能单靠等待证明对象元数据正确。
Kubernetes 的终止顺序见[官方说明](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination-flow)。
固定上游参数和网络机制分别见 [server-main.go](https://github.com/minio/minio/blob/9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a/cmd/server-main.go)、
[storage-rest-client.go](https://github.com/minio/minio/blob/9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a/cmd/storage-rest-client.go) 和
[internal/rest/client.go](https://github.com/minio/minio/blob/9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a/internal/rest/client.go)。

## 最终配置复测

使用原 x86 三台池化 VM，以及用户提供的 ARM 主机中的三个 Kubernetes 节点容器。
ARM 三节点共用物理主机，本轮不是物理主机故障认证。全部运行时测试在获准测试机上进行。
已有 107 个对象在配置升级后逐个验证，再在单节点离线时写入两个新对象，最终 109 个。
每次全量校验前清空本地回读目录，比较独立保存的 SHA256；不手动 heal，不重写旧对象。

恢复过程中仍存在短暂连接失败。另观察到个别 Pod 启动时 DNS 自识别尚未一致，
MinIO 报 `local host () not found in cluster setup` 后由 Kubernetes 自动重试，随后恢复并通过全量校验。
这不是“启动零重试”或“零中断”认证；本轮的目标是既有对象不再被误报 404，以及启停后的持久化正确性。

| 全套分布式/启停：HTTP 200 | 13108 | 14488 |
| 已存在对象错误 404 | **0** | **0** |

最后额外关闭诊断跟踪，是为了排除长连接对终止时序的影响。每个架构合计十二次 Pod 重建。
不同实验时长/次数不同，计数不能直接当作故障概率比较。

两边均通过：单节点运行时停启期间的读写、恢复后三盘在线、九次连续 Pod 重建、
同 Pod 内 MinIO SIGKILL（检查组件没有重启且新进程重新准入）、全部缩容到 0 再恢复。
最终每边 109 个对象 SHA256 一致，原始 107 个对象哈希保持不变；3 个 PVC UID/卷名保持不变，
每块盘的 distributed 桶各有 109 份对象元数据。九次重建的恢复时间 x86 为 41–56 秒，ARM 为 51–57 秒。

显式已知对象适配器：x86 成功 9393 次；ARM 成功 12002 次、3 次重试耗尽返回 exit75，
均由传输失败导致；尝试阶段没有错误 404。它不是普通客户端必经路径，主要验收仍看上表的无重试 GET。
负向检查两边均通过：真正缺失对象仍为 404，错误凭据仍为 403，哈希不符拒绝输出，五次耗尽返回临时不可用。
跟踪中的桶锁配置 404 和负向用例的正常缺失 404 均单独识别，没有混入“已存在对象错误 404”统计。

## 结论与使用边界

**这组上层配置通过了本轮双架构错误 404 与持久化验收，无需修改 MinIO 源码。**
单独延长退出时间未通过 ARM；需要同时处理 DNS 刷新和有序退出。证据支持该组合在本次场景有效，
不等于修改了上游读仲裁逻辑，也不保证任意网络分区、双节点同时故障或其他拓扑下都不会错误 404。
PreStop 不覆盖 SIGKILL、断电或强制零宽限删除；本轮另测了单节点运行时故障和单进程 SIGKILL，
但不是物理主机故障认证。DNS 刷新频率提高、计划停机时间增加，扩大规模或升级 MinIO 版本需重新验证。

现有 Helm release 升级需显式设置 `--set-string dnsCacheTTL=1s --set shutdownDrainSeconds=10`，
保留原 Secret/PVC。由于使用 OnDelete，仅升级模板不会重启现有 Pod，需按计划逐个重建并验证恢复。
测试脚本和原配置/排流单项/组合配置的复测方法见 [tests/drain](deployment/tests/drain/README.md)。
本轮只提交配置、脚本和报告，没有发版。
